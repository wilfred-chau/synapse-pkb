# plan-before-code

这个 skill 用于在 **`doc-pilot` 全程值守** 的前提下，把用户需求先转化成一份可确认的实现方案，
再把方案摘要交给 `dev-with-ticket` 用于建票。它不是脱离 `doc-pilot` 单独运行的前置流程，
也不是每次开发都必须触发的固定步骤，而是用于**中大型任务的“方案先行”环节**。

## 定位

三个 skill 的关系是**嵌套值守关系**，不是线性流水线：

- `doc-pilot`：全程值守，负责项目上下文持续读取、规范监督、状态回写
- `plan-before-code`：在 `doc-pilot` 值守下，把需求转化为方案并和用户确认
- `dev-with-ticket`：在 `doc-pilot` 值守下，基于已确认的方案摘要建票，并承接后续开发前置确认

换句话说：

- `doc-pilot` 不会因为进入 `plan-before-code` 或 `dev-with-ticket` 而暂停
- `plan-before-code` 是 `dev-with-ticket` 建票前的一个具体环节
- 只有在任务复杂度值得先出方案时，才触发本 skill

## 触发条件

对应 `doc-pilot` 任务分级中的 **L3/L4**，满足任一条件时触发：

- 用户提出的功能开发涉及**新增模块**
- 需求涉及**跨多个文件**的改动（`doc-pilot` 会给出预计涉及文件数作为参考线）
- 改动会影响**现有数据结构**或**接口契约**
- 明显复杂的 bug 修复，且**排查思路不明确**或**可能有多种修复路径**
- 属于 L4（跨模块、影响架构、数据库结构变更、多阶段实施）的任务无条件触发本 skill

## 不触发条件

以下情况不要触发，避免过度流程化：

- 单文件小改动
- 样式调整
- 简单的一行修复
- 用户已经给出明确到可以直接开发的实现步骤
- 用户明确说“**不需要出方案，直接改**”

## 执行原则

本 skill 运行时，必须默认 `doc-pilot` 仍在值守：

1. 方案生成依赖 `doc-pilot` 已读取的项目上下文
2. 方案确认过程中仍受 `doc-pilot` 的范围约束、规范约束和文档语境约束
3. 方案确认后，仍由 `doc-pilot` 继续监督后续建票、开发和收工写回

不要把本 skill 理解为“替代文档阅读”或“替代建票”，它只负责**需求到方案的转化与确认**。

## 本地方案落盘要求

凡是实际触发了本 skill 的任务，在向用户展示方案前，必须先把方案落到 `docs/plans-local/` 下的独立任务目录中。

- 目录建议：`docs/plans-local/<yyyy-mm-dd>-<topic>/`
- 最少文件：
  - `plan.md`：需求理解、范围、实现步骤、风险与决策
  - `checklist.md`：按执行顺序拆开的任务清单
- 该目录只用于本地协作和会话沉淀，**永远不需要上传到代码仓库**
- 若仓库尚未忽略 `docs/plans-local/`，需先补 `.gitignore`
- Jira ticket 创建后，可回写 ticket 编号到上述文件，保证方案、工单、实现三者可串联

## 执行流程

### 1. 基于 doc-pilot 上下文生成方案

在 `doc-pilot` 已经读取到的项目文档上下文基础上，输出一份结构化方案，至少包含：

- **需求理解复述**
  - 用自己的话复述用户真实意图
  - 重点对齐“要解决什么问题”而不是直接跳到实现
- **涉及的模块 / 文件范围**
  - 哪些模块会被触及
  - 哪些文件预计需要修改或新增
- **具体实现步骤**
  - 分点列出
  - 保持有执行顺序感
  - 优先写最小闭环路径
- **潜在风险点 / 需要确认的技术决策**
  - 只列真正会影响实现路径的分叉
  - 若无关键分叉，可明确写“暂无额外确认项”

### 2. 向用户展示方案并等待确认

方案输出后必须：

- 明确告诉用户：**先确认方案，再建票，再开发**
- 展示给用户的方案内容应与 `docs/plans-local/.../plan.md` 保持一致
- 等待用户确认或修改意见
- 未经确认，不进入 `dev-with-ticket`
- 不因为用户说“继续”就默认方案已确认，除非上下文明确表达认可

### 2.1 若存在跨会话任务记录，同步更新阶段

若本次任务已由 `doc-pilot` 创建了跨会话任务记录（通常见于 L4，或预计跨会话的 L3），
方案输出后将其阶段更新为"方案确认中"；用户确认后更新为"已确认待建票"。不存在任务记录
的任务跳过本步骤。

### 3. 把方案摘要传给 dev-with-ticket

用户确认无误后：

- 从已确认方案中提炼一版简洁摘要
- 将该摘要作为 Jira Description 传给 `dev-with-ticket`
- Ticket 标题保持简洁，Description 则体现本次已确认的实现方案与范围

### 4. 后续照常进入建票与开发

方案确认后，后续流程按现有 `dev-with-ticket` 规则执行：

- 创建 ticket
- 回报 ticket 编号给用户确认
- 用户确认后再开始开发
- 收工时 commit message 草案带 ticket 编号

整个过程中，`doc-pilot` 继续负责：

- 上下文持续读取
- 范围约束监督
- 收工文档回写

## 推荐输出格式

建议用下面这种结构输出方案：

```markdown
## 需求理解
- ...

## 涉及范围
- 模块：
- 文件：

## 实现步骤
1. ...
2. ...
3. ...

## 风险与待确认项
- ...
```

如果任务已经足够清晰，也不要为了“显得正式”而把方案写得过长。重点是帮助用户确认理解，而不是制造文档负担。

## 与 doc-pilot 的配合约束

- 本 skill 默认 `doc-pilot` 已经在当前任务中生效
- 若发现当前任务其实还没完成 `doc-pilot` 的必要文档读取，应先回到 `doc-pilot` 路由补齐上下文
- 若收工时用户认可且方案具有复盘价值，可选归档到 `docs/plans/`

归档建议：

- 文件名：`<TICKET-KEY>-plan.md`
- 示例：`SPKB-12-plan.md`

但是否归档仍受 `doc-pilot` 的整体值守和文档策略约束，不强制每次都写。

## 与 dev-with-ticket 的配合约束

- 本 skill 不直接建票
- 本 skill 只负责把“未经确认的需求”变成“已确认的实现方案”
- 建票仍由 `dev-with-ticket` 执行
- 传给 `dev-with-ticket` 的应是**方案摘要**，不是未整理的原始需求文本

## 何时跳过本 skill

即使是开发任务，满足以下任一情况也应主动跳过：

- 用户明确要求直接开发
- 改动范围明显很小
- 当前需求已经给出明确实现步骤，继续出方案只会重复用户内容

跳过时可直接说明：

```text
这次任务范围比较小 / 实现路径已经足够明确，我先不单独走 plan-before-code，直接进入建票或开发环节。
```

## 收工提醒

若本次任务经过了 `plan-before-code`：

- 收工汇报可注明“本次按方案先行流程执行”
- 若有 ticket，commit message 草案需带 ticket 编号
- 仍需给出建议 `git add` 文件清单
