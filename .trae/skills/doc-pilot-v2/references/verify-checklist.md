# doc-pilot 验证清单（新会话提示词测试集）

> 用途：新开会话逐条投喂下列提示词，验证 skill 路由与行为是否符合预期。
> 用法：第一部分路由测试（T1~T12）**每条开独立新会话**——同一会话里 skill 一旦激活，
> 后续提问测不出「激活」只测得出「路由」。使用前把 `<模块>`、`<编号>` 等占位符替换成
> 你项目里真实存在的名字/编号，否则测试没有意义。
> 叫停时机：开发/修 bug/写用例类提示词在完成「预期第一动作」后即可说「测试结束，先停」，
> 不必让任务真跑完。
> 记录：每条在「结果」列记 ✓/✗，末尾按汇总标准判定。

## 零、初始化测试（仅新项目，只需跑一次）

| # | 测点 | 提示词 | 预期第一动作 / 通过标准 | 结果 |
| --- | --- | --- | --- | --- |
| T0 | 首次初始化 | （在没有 docs/.doc-pilot.json 的项目里）继续开发 <模块> | AI 先说明未检测到知识库配置，简短询问项目名等几项，随后运行 `scripts/init-kb.py` 生成 `docs/` 骨架，再继续处理原请求 | ☐ |

## 一、路由触发测试（每条独立新会话，需项目已初始化）

| # | 测点 | 提示词（替换占位符后复制即用） | 预期第一动作 / 通过标准 | 结果 |
| --- | --- | --- | --- | --- |
| T1 | 开发路由 | 继续开发 <模块> | （git 项目）先做分支同步检查，再读 `docs/progress/STATUS.md` → `overview/architecture-snapshot.md`，能说出该模块待办后才动手 | ☐ |
| T2 | 规划路由 | 规划一下 <某功能> 怎么实现 | 同 T1 开工读档；若启用需求源，应查 `requirements/requirements-full.md` 相关定义行再谈方案 | ☐ |
| T3 | 需求速查（需启用需求源） | <编号> 是什么？ | 检索 `requirements-full.md` 编号定义表，引用原文作答，注明出处；不整读开工文档 | ☐ |
| T4 | 速查＋进展 | <编号> 是干嘛的？做完了没？ | 先引需求原文，再补 `STATUS.md` 说明实现现状——需求定义与实现现状**分开答** | ☐ |
| T5 | 修bug·报错现象 | <描述一个真实症状> 帮我排查 | 第一动作**检索 `docs/bugs/BUGFIX_LOG.md`**（含 history 历史卷），命中则引用其根因/经验教训 | ☐ |
| T6 | 修bug·关键词 | <另一个真实症状>，排查一下 | 先检索 `docs/bugs/` 相似案例；未命中则查 overview 横切机制再定位代码 | ☐ |
| T7 | 测试任务 | 给 <模块> 补几个测试用例 | 先读 `docs/qa/` 下相关测试规划文档 | ☐ |
| T8 | 元路由·用法 | doc-pilot 怎么用？ | 读取并**完整展示** `references/usage-guide.md`，不自由发挥 | ☐ |
| T9 | 元路由·清点 | 这个项目里有什么 skill 工具？ | 动态列出当前项目 skills 目录清单，再展示 usage-guide.md | ☐ |
| T10 | 架构调研 | 梳理一下这个系统的现状 | 精读 `overview/architecture-snapshot.md`；能说出横切机制且与文档一致 | ☐ |
| T11 | 部署运维 | 说明一下部署和回滚步骤，先不要实际执行 | 先读 `docs/deploy/DEPLOYMENT.md` 再作答，内容与该文档一致 | ☐ |
| T12 | 模式A·整理 | 整理一下文档 | 走模式 A 七步；当前根目录干净应报「无需归档」；跑 `python scripts/check-docs.py` 报全绿 | ☐ |
| T13 | 状态查询 | <模块> 做完了吗？ | 查 `STATUS.md` 模块表作答，不混入需求定义 | ☐ |
| T14 | 手动点名 | 按 doc-pilot skill 开工，继续 <模块> | 100% 激活；行为同 T1 | ☐ |

## 二、行为细节测试（可在任意会话内追加）

| # | 测点 | 操作 | 通过标准 | 结果 |
| --- | --- | --- | --- | --- |
| B1 | 区分口径切换 | 同一会话先问「<编号> 是什么？」，得到答案后再说「那开始开发它」 | 第一问走需求速查；第二问切换为模式 B 开工读档 | ☐ |
| B2 | 纠偏话术 | 若 AI 没读文档就直接动手，说「先读 docs/progress/STATUS.md 再动手」 | 立即纠正，转去读 STATUS 后再继续 | ☐ |
| B3 | 纯查询不写回 | 完成 T3/T4 后查看 `docs/progress/dev-log.md` 尾部 | 无为纯查询新增的条目 | ☐ |
| B4 | 校验命令 | 问「怎么验证知识库健康？」 | 答出 `python scripts/check-docs.py` 及其检查项概述 | ☐ |
| B5 | 分支同步检查（仅 git 项目） | 告知「同事刚往远程推了新提交」 | AI 主动 `git fetch` 并比对上游，确认落后后 `git pull --ff-only`，按记录规范留痕 | ☐ |
| B6 | 工单门可关闭 | 若项目 `ticket_system.enabled = false`，走一次开发任务 | 收工汇报中不出现任何票号/建票相关内容 | ☐ |

## 三、收工闭环测试（可选，会真实改动文件，安排在最后）

完整跑一个小任务（如真继续某模块的第一步），验证收工写回闭环：

- [ ] `dev-log.md` 按模板追加（背景/产出/验证/遗留四段式）
- [ ] `STATUS.md` 刷新：模块表、最近动态、更新日期（含隐藏标记）
- [ ] 若修了 bug：`BUGFIX_LOG.md` 新条目编号 = 全库最大 + 1，按模板五段式
- [ ] `python scripts/check-docs.py` 全绿
- [ ] 测试完 `git commit`（若为 git 项目）

## 四、汇总标准

- **T0（若适用）+ T1~T14 全命中 + B1~B6 通过** = skill 健康，可放心日常使用。
- **个别未命中**：记录提示词原话与实际走向，对照 `references/duty-routes.md` 触发词表补词——
  修改须在 SKILL.md description / SKILL 正文 / duty-routes 三处同步，并追加 dev-log。
- **系统性不命中**（如完全不读文档）：属 skill 未激活问题，检查项目 skills 目录是否正确
  安装了本 skill。

## 附：注意事项

1. 排查类测试（T5/T6）若未让 AI 真修，结束时不应出现新的 BUG 条目；若真修了，核对编号规则。
2. T3/T4 的标准答案以 `docs/requirements/requirements-full.md` 编号定义表为唯一权威（若启用）。
3. 开发类测试叫停后，AI 不应留下半成品写回（叫停即无产出，无写回属正常）。
