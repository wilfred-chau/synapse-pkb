# Skill 职责边界

多个 skill 协作时最容易出的问题不是"某个 skill 写得不好"，而是职责互相重叠、谁都觉得
某件事是自己该管、又都没管全。这份文件把每个角色的职责边界写清楚，谁的职责就只归谁，
其他 skill 不代劳、也不重复定义。

## CLAUDE.md（或等价的项目规则文件）

负责项目级别的永久性事实和约束：项目定位、技术栈基线、范围边界、执行风格、以及"什么情况
下自动触发哪个 skill"这类路由规则。不负责任何运行时的具体任务处理逻辑——那是各个 skill
自己的事。

## doc-pilot

负责：
- 项目上下文的持续读取（知识库、进度、历史经验）
- 任务分级判断与工作流路由
- 规范监督（三条铁律、验证要求、容量红线）
- 跨会话任务记录的创建与维护
- 知识库写回（dev-log、STATUS、BUGFIX_LOG、架构快照）

不负责：
- 具体的技术方案设计（那是 plan-before-code 的事）
- 工单系统的查重、草稿确认、实际建票（那是 dev-with-ticket 的事）

## plan-before-code

负责：
- 需求理解复述，确认和用户的意图对齐
- 涉及模块/文件范围的判断
- 具体实现步骤的拆解
- 风险点识别，验收标准的初步设定

不负责：
- 项目长期记忆的维护（不读写 dev-log/STATUS，这是 doc-pilot 的事）
- 工单创建（方案确认后交给 dev-with-ticket，自己不建票）

只在 doc-pilot 判断任务分级达到 L3/L4（或用户明确要求先出方案）时被触发，不单独运作。

## dev-with-ticket

负责：
- 建票前的查重检查
- 票据标题/描述的草稿生成与确认
- 实际调用工单系统 API 完成建票，回报票号

不负责：
- 技术方案设计（如果任务需要方案，方案已经由 plan-before-code 在建票前完成，本 skill
  只是把方案摘要放进票据描述，不重新设计）
- 项目知识库维护

在 doc-pilot 判断需要建票（工单系统已启用，且完成了必要的开工读取/方案确认）时被触发。

## 三者的协作关系

不是线性的"一个做完交给下一个"流水线，而是 doc-pilot 全程值守、其余两个 skill 在需要时
被引入、完成各自的单一职责后退出，doc-pilot 继续负责后续的验证监督和收工写回。这样任何
一个环节被跳过或者用户中途改变主意，doc-pilot 仍然掌握全局状态，不会因为某个协作 skill
的中断而丢失上下文。
