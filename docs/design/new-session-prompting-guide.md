# synapse-pkb 项目新会话提示词指南

> 面向所有参与项目的开发人员。目标不是让开发者背 skill 名字或手动选择流程，而是让开发者用尽量自然、简短的方式表达任务，由 agent 在项目规则下自动判断该采用哪种工作模式。

## 1. 设计目标

这份指南服务于一个很明确的目标：

**开发者少写流程，agent 多做判断。**

也就是说，本项目并不希望开发者在每次开启新会话时，都显式写出：

- 要不要先读文档
- 要不要先出方案
- 要不要先建 ticket
- 要不要走哪个 skill

这些应当由 agent 根据任务内容自主判断。

## 2. 推荐使用方式

在绝大多数情况下，开发者应优先使用自然表达。

例如：

```text
开发需求文档里的 A1 部分
```

```text
修复条目录入后摘要未生成的问题
```

```text
整理一下部署文档
```

这类表达就是项目推荐写法，不需要额外补“按什么模式处理”。

## 3. agent 的默认职责

当开发者发起任务后，agent 应自动完成以下判断：

1. 识别任务类型：开发、修 bug、整理文档，还是其他任务
2. 判断任务复杂度：是小改动，还是中大型任务
3. 判断是否需要读取项目文档上下文
4. 判断是否需要先形成方案
5. 判断是否需要先创建 Jira ticket
6. 判断是否需要回头向用户确认关键分叉点

项目 skill 的存在，是为了把这套判断能力沉淀到 agent 侧，而不是增加开发者负担。

## 4. 三类核心场景的推荐写法

### 4.1 开发

推荐直接这样写：

```text
开发需求文档里的 A1 部分
```

```text
继续开发基础平台模块
```

```text
实现条目录入的最小闭环
```

```text
把 backend 的健康检查接口补上
```

对于这类输入，agent 应自行判断：

- 是否先由 `doc-pilot` 读取上下文并持续值守
- 是否属于中大型任务，需要进入 `plan-before-code`
- 是否在确认方案后再通过 `dev-with-ticket` 建票

### 4.2 修复 bug

推荐直接这样写：

```text
修复首页白屏问题
```

```text
修复条目录入后摘要未生成的问题
```

```text
排查一下检索结果为空的问题
```

```text
看下这个报错为什么会出现
```

对于这类输入，agent 应自行判断：

- 是否先查询 bug 历史记录
- 是否可以直接修
- 是否属于复杂 bug，需要先排查或先出方案
- 是否先创建 Jira ticket

### 4.3 整理文档

推荐直接这样写：

```text
整理项目文档
```

```text
整理一下部署文档
```

```text
把散落的 markdown 归档进 docs
```

```text
初始化文档库
```

对于这类输入，agent 应默认按 `doc-pilot` 路由处理，不要求开发者点名 skill。

## 5. 开发者真正需要说清楚的内容

虽然本项目追求“少写提示词”，但如果能补充下面几类信息，agent 的判断会更稳。

### 5.1 任务目标

这是必须的。至少要说清楚“要做什么”。

例如：

- 开发需求文档里的 A1 部分
- 修复首页白屏问题
- 整理部署文档

### 5.2 作用范围

如果已经知道改动范围，补一句会更好，但不是强制。

例如：

- 只看 backend
- 先改 frontend 首页
- 只整理 docs/deploy

### 5.3 明确边界

如果有不希望触碰的部分，最好显式说明。

例如：

- 不要提前做语音模块
- 先不要改数据库结构
- 只做需求文档里的一期范围

## 6. 什么时候才需要额外说明

默认情况下，不需要手动指定 skill。

只有下面几类情况，才建议额外补一句：

### 6.1 你希望先出方案

```text
开发需求文档里的 A1 部分，先给我方案，我确认后再开始开发
```

### 6.2 你希望直接改，不经过方案环节

```text
修这个问题，不需要先出方案，直接改
```

### 6.3 你希望控制改动边界

```text
开发 A1 部分，只改 backend，先不要动数据库和前端
```

这里也不要求开发者写出 `plan-before-code` 或 `dev-with-ticket` 的名字。  
只要把意图说清楚，agent 应负责映射到合适的 skill 和流程。

## 7. 三类场景的最小模板

### 7.1 开发

```text
开发 <需求/模块/功能>
```

示例：

```text
开发需求文档里的 A1 部分
```

### 7.2 修复 bug

```text
修复 <问题现象>
```

示例：

```text
修复条目录入后摘要未生成的问题
```

### 7.3 整理文档

```text
整理 <文档范围>
```

示例：

```text
整理部署文档
```

## 8. 推荐的简洁增强版写法

如果开发者愿意多补一句信息，推荐使用下面这种简洁写法：

### 8.1 开发

```text
开发需求文档里的 A1 部分，只做 backend，先不要动数据库
```

### 8.2 修 bug

```text
修复首页白屏问题，先看 frontend 首页入口
```

### 8.3 整理文档

```text
整理部署文档，把能归档进 docs 的都归档好
```

## 9. 不推荐的写法

以下写法仍然不理想：

```text
帮我搞一下
继续
你看着办
这个处理一下
```

问题不在于它们没有点名 skill，而在于：

- 没说清楚要做什么
- 没说清楚对象是什么
- agent 很难判断任务边界

## 10. 项目推荐原则

### 10.1 对开发者

- 尽量自然说人话
- 优先说明任务目标
- 有边界时补一句限制条件
- 不要求背 skill 名称
- 不要求手动选择流程模式

### 10.2 对 agent

- 主动识别任务类型
- 主动判断复杂度
- 主动决定是否需要先出方案
- 主动决定是否需要先建 ticket
- 主动读取并维护项目文档上下文
- 仅在关键分叉处再向用户确认

## 11. 审核重点

在正式投入使用前，审核应重点关注以下问题：

- [ ] 这份文档是否真正降低了开发者写提示词的负担
- [ ] 是否允许开发者用非常自然的表达直接发起任务
- [ ] 是否把流程复杂度更多收敛到了 agent 侧
- [ ] 是否保留了边界场景下的人工控制能力
- [ ] 是否符合本项目当前的 skill 设计目标

## 12. 一句话结论

本项目追求的不是“开发者写复杂提示词来驱动 skill”，而是：

**开发者尽量自然表达任务，agent 根据项目规则自主判断该走哪种模式。**
