# synapse-pkb 项目新会话提示词指南

> 面向所有参与项目的开发人员。目标是在**开启全新会话窗口**时，通过规范的提示词写法，稳定触发项目已预设的核心 skill，减少上下文偏差、流程遗漏和返工。

## 1. 文档目标

本指南用于统一新会话中的提示词编写规范，帮助开发人员在以下三类核心场景中，准确触发项目 skill：

- 开发
- 修复 bug
- 整理文档

本项目当前相关核心 skill 及其职责分工如下：

- `doc-pilot`：全程值守，负责项目上下文持续读取、规范监督与状态回写
- `plan-before-code`：在 `doc-pilot` 值守下，对中大型任务先产出实现方案并等待确认
- `dev-with-ticket`：在 `doc-pilot` 值守下创建 Jira ticket，并在确认后进入开发

## 2. 总体原则

### 2.1 新会话提示词的基本目标

一条高质量的新会话提示词，至少要让 AI 明确三件事：

1. 你现在要做的任务类型是什么
2. 本次任务的范围和边界是什么
3. 是否需要走额外流程（出方案、建 ticket、直接开发等）

### 2.2 推荐写法

为保证 skill 触发稳定，建议在提示词中同时包含：

- **任务类型词**：开发 / 修复 bug / 整理文档 / 继续开发 / 重构 / 规划
- **对象范围**：模块、目录、接口、数据结构、页面、文件
- **流程要求**：是否要先出方案、是否要先建 ticket、是否可以直接改
- **限制条件**：不能改哪里、只改哪些文件、是否允许调整接口或数据结构

### 2.3 最稳妥的触发策略

如果任务比较重要，建议**显式点名 skill 名称**，因为这会比纯语义触发更稳定。

推荐优先级：

1. `按 doc-pilot ...`
2. `按 doc-pilot + plan-before-code ...`
3. `按 doc-pilot + dev-with-ticket ...`
4. `按 doc-pilot + plan-before-code + dev-with-ticket ...`

## 3. skill 触发关系速查

| 场景          | 推荐 skill 组合                                            | 说明                                    |
| ------------- | ---------------------------------------------------------- | --------------------------------------- |
| 小型开发      | `doc-pilot` + `dev-with-ticket`                        | 需求明确、无需单独出方案                |
| 中大型开发    | `doc-pilot` + `plan-before-code` + `dev-with-ticket` | 先出方案并确认，再建票，再开发          |
| 简单 bug 修复 | `doc-pilot` + `dev-with-ticket`                        | 先查 bug 历史，再建票，再修             |
| 复杂 bug 修复 | `doc-pilot` + `plan-before-code` + `dev-with-ticket` | 根因不明或修复路径有分叉时先出方案      |
| 整理文档      | `doc-pilot`                                              | 由 doc-pilot 主导，不需要 plan / ticket |

## 4. 场景一：开发

### 4.1 何时只用 `doc-pilot + dev-with-ticket`

适用于：

- 改动范围较小
- 需求已经明确
- 不涉及新增模块
- 不涉及跨多个文件的大范围改动
- 不影响现有数据结构或接口契约

### 4.2 何时加上 `plan-before-code`

满足任一情况时，推荐在提示词里显式要求 `plan-before-code`：

- 需要新增模块
- 会改多个文件
- 会影响数据库结构
- 会影响接口输入输出
- 会影响现有模块间协作关系
- 你自己也还不完全确定实现路径

### 4.3 开发类提示词必备要素

- 任务目标
- 所属模块或功能域
- 范围限制
- 是否需要先出方案
- 是否允许直接开发

### 4.4 标准模板

#### 模板 A：小型开发

```text
按 doc-pilot + dev-with-ticket 流程继续开发 <模块名>。
本次目标：<一句话目标>。
范围：<限定目录/文件/页面/接口>。
限制：<不允许改动的内容>。
如果需求已经足够明确，就直接建 ticket 并开始开发。
```

#### 模板 B：中大型开发

```text
按 doc-pilot + plan-before-code + dev-with-ticket 流程处理这个开发任务。
目标：<一句话描述要做什么>。
背景：<为什么要做 / 当前缺什么>。
预期影响范围：<模块/接口/数据库/页面>。
要求：先给出结构化实现方案，等我确认后再建 ticket 和开发。
限制：<不允许改动的范围 / 必须遵守的约束>。
```

### 4.5 示例

#### 示例 1：小型开发

```text
按 doc-pilot + dev-with-ticket 流程继续开发 backend 的健康检查接口。
本次目标：补一个基础的 /api/health 接口，供前后端联调使用。
范围：只改 backend 里的 controller 和必要配置。
限制：不要引入数据库访问，不要扩展成业务接口。
```

#### 示例 2：中大型开发

```text
按 doc-pilot + plan-before-code + dev-with-ticket 流程处理条目录入模块开发。
目标：开始做基础平台里的 Entry 录入最小闭环。
背景：现在前后端只有骨架，还没有真正的业务链路。
预期影响范围：backend、frontend、数据库表结构、接口契约。
要求：先给我一份结构化实现方案，确认后再建 ticket 和开发。
限制：严格按需求文档的一期范围做，不要提前碰语音模块。
```

### 4.6 注意事项

- 不要只说“帮我做一下这个功能”，否则范围太模糊
- 涉及中大型改动时，最好显式写“**先出方案，再建票，再开发**”
- 如果你明确不想走方案环节，要直接写：`不需要出方案，直接改`

## 5. 场景二：修复 bug

### 5.1 何时只用 `doc-pilot + dev-with-ticket`

适用于：

- 报错位置明确
- 修复点明显
- 不涉及多路径取舍
- 不涉及接口契约或数据结构变化

### 5.2 何时加上 `plan-before-code`

满足任一情况时推荐加上：

- 根因不明确
- 需要先排查再决定修法
- 可能有多种修复路径
- 改动可能影响多个模块
- 你怀疑问题不止一处

### 5.3 bug 修复类提示词必备要素

- 现象描述
- 影响范围
- 复现线索
- 是否允许先排查后给方案
- 是否要求先建票

### 5.4 标准模板

#### 模板 A：简单 bug

```text
按 doc-pilot + dev-with-ticket 流程修这个 bug。
现象：<报错现象>。
范围：<模块/接口/页面>。
已知线索：<日志/报错信息/复现步骤>。
如果修复路径明确，就直接建 ticket 后开始修。
```

#### 模板 B：复杂 bug

```text
按 doc-pilot + plan-before-code + dev-with-ticket 流程排查并修复这个 bug。
现象：<报错现象>。
影响：<影响用户/模块/链路>。
已知线索：<日志、堆栈、复现步骤、怀疑点>。
要求：先给排查思路和修复方案，我确认后再建 ticket 和动代码。
限制：<不希望动的模块 / 兼容性要求>。
```

### 5.5 示例

#### 示例 1：简单 bug

```text
按 doc-pilot + dev-with-ticket 流程修复 frontend 首页白屏问题。
现象：打开首页后控制台报一个空指针错误，页面不渲染。
范围：只看 frontend 首页入口和相关组件。
已知线索：问题出现在我刚加的状态初始化逻辑之后。
```

#### 示例 2：复杂 bug

```text
按 doc-pilot + plan-before-code + dev-with-ticket 流程排查并修复条目录入后摘要未生成的问题。
现象：录入成功了，但后续摘要和向量化都没有执行。
影响：会导致后续检索链路不可用。
已知线索：目前不确定是任务调度、数据库状态，还是 AI 处理链路的问题。
要求：先给我排查思路、可能根因和建议修复路径，确认后再建 ticket 和修复。
```

### 5.6 注意事项

- bug 场景下不要只说“修一下这个问题”
- 至少要给出现象和影响，否则很难触发高质量排查
- 如果你怀疑是复杂问题，提示词里要明确写“**先排查并给方案**”

## 6. 场景三：整理文档

### 6.1 推荐 skill

文档整理类任务通常只需要 `doc-pilot`。

这类任务本身不需要 `plan-before-code`，也通常不需要 `dev-with-ticket`。

### 6.2 文档整理类提示词必备要素

- 任务类型：整理 / 归档 / 重构文档 / 初始化文档库
- 对象范围：全仓库 / 某个目录 / 某类文档
- 目标：归档、补索引、规范命名、清理散落文档等

### 6.3 标准模板

```text
按 doc-pilot 流程整理项目文档。
范围：<全仓库 / docs / 某个目录>。
目标：<归档、补索引、统一命名、修复链接、补充缺失文档>。
如果发现散落文档，请按 docs 结构归类并更新 README 索引。
```

### 6.4 示例

#### 示例 1：整理全仓库文档

```text
按 doc-pilot 流程整理项目文档。
范围：全仓库。
目标：把散落的 Markdown 文档归档进 docs，补 README 索引，并修复旧链接。
```

#### 示例 2：整理某一类文档

```text
按 doc-pilot 流程整理部署文档。
范围：docs/deploy。
目标：检查现有部署文档是否完整，补缺失说明，并把敏感信息与可入库文档边界整理清楚。
```

### 6.5 注意事项

- 文档任务要明确“整理什么、整理到什么程度”
- 如果目标是“初始化文档库”，最好直接写出来
- 如果只是想查询某个文档内容，不要误写成“整理文档”

## 7. 推荐的新会话提示词结构

建议所有开发人员在新会话里优先采用以下结构：

```text
按 <skill 组合> 流程处理这个任务。
任务类型：<开发 / 修 bug / 整理文档>
目标：<一句话目标>
背景：<为什么要做>
范围：<模块/文件/目录/接口/数据库>
要求：<是否先出方案 / 是否直接开发 / 是否先建票>
限制：<不能改哪里 / 必须遵守什么规则>
```

## 8. 常见反例

以下写法不推荐：

```text
帮我改一下
继续搞
这个有问题你看下
整理一下吧
```

问题在于：

- 任务类型不明确
- 范围不明确
- 无法判断是否要触发 `plan-before-code`
- 无法判断是否该直接建票或直接开发

## 9. 审核组织建议

在正式启动项目开发前，建议按以下方式完成本指南审核：

### 9.1 建议审核对象

- 项目负责人
- 参与本项目的后端开发人员
- 参与本项目的前端开发人员
- 需要频繁开启新会话的 AI 协作者

### 9.2 审核重点

- 提示词规范是否清晰易懂
- 三类核心场景是否覆盖完整
- skill 触发关系描述是否准确
- 示例模板是否能被直接复制使用
- 是否符合项目当前实际流程

### 9.3 审核清单

- [ ] 是否清楚解释了 `doc-pilot`、`plan-before-code`、`dev-with-ticket` 的分工
- [ ] 是否明确区分了“小型开发”和“中大型开发”
- [ ] 是否明确区分了“简单 bug”和“复杂 bug”
- [ ] 是否说明了哪些场景不应该触发 `plan-before-code`
- [ ] 是否给出了可直接复制的新会话模板
- [ ] 是否对“整理文档”场景提供了独立规范
- [ ] 是否提醒了范围、限制和流程要求这几个必备要素

### 9.4 审核输出要求

审核完成后，建议至少给出以下结论之一：

- 可直接投入项目使用
- 需要补充场景示例后再投入使用
- 需要调整 skill 触发说明后再投入使用

## 10. 一句话结论

如果想稳定触发项目核心 skill，最稳的做法不是“只描述需求”，而是：

**在新会话第一条消息里明确写出任务类型、范围、流程要求和限制条件，并在必要时直接点名 skill。**
